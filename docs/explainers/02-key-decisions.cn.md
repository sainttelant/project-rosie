关键架构决策

Project Rosie 中每一个"不那么显然"的选择，以及背后的原因。写下来的目的，是让未来的贡献者——或者黑客松评委——无需追问就能理解这些推理。

决策 1 —— 从 VCF 起步，而非 FASTQ

我们的选择： 流水线以上游传入的经 VEP 注释的 VCF 文件为起点，而不是原始测序 read。

我们跳过了什么： 完整流水线中的第 1–3 步（测序、比对、通过 BWA-MEM2 / GATK Mutect2 做变异检测）。

原因：
• 任何临床测序工作流本身都会产出 VCF。做全外显子组测序的兽医肿瘤学实验室，交付物就是一份 VCF。

• 序列比对与变异检测都已是解决的问题，且拥有成熟的工具链。把它们加进来会让范围翻倍，却带不来任何新意。

• 真正尚未解决的可及性问题，是"从 VCF → 排序候选 → 临床报告"这一段。这才是我们在构建的东西。

• 对一场只有 10 天的黑客松而言，从 VCF 起步能让我们交付出真实、可演示的成果。

代价： 用户必须自行提供一份已经完成变异检测的 VCF。对于第二阶段（临床部署），我们会把 FASTQ → VCF 集成为一个可选的上游步骤。

决策 2 —— 选 NetMHCpan，而非 MHCflurry

我们的选择： 采用 NetMHCpan 4.2 作为结合亲和力预测器。

为什么不用 MHCflurry：
• MHCflurry 是 Python 原生的、易于安装，但它主要基于人类 HLA 等位基因训练。

• 对于犬类数据（核心用例），我们需要 DLA 等位基因支持——即 HLA 在犬类中的对应物。NetMHCpan 支持 DLA 等位基因。

• MHCflurry 与已安装的 TensorFlow 版本还存在 Keras 3 不兼容问题，会导致运行时报错。

代价： NetMHCpan 默认通过 IEDB REST API 调用，速度较慢（955 个突变约需 45 分钟）。本地二进制更快（约 2 分钟），但要求以 wrapper 形式安装 IEDB Analysis Resource 工具包——这与 DTU 二进制是分开的。目前可以接受，已记录为第二阶段的优化项。

决策 3 —— 第一阶段不使用 AlphaFold

我们的选择： 在初始流水线中跳过结构验证（AlphaFold2 表面暴露检查）。

原因：
• AlphaFold 会显著增加计算时间与基础设施复杂度（要达到合理速度需要 GPU）。

• IC50 结合分数 + VAF 的综合评分，已足以产出一份排序合理、临床上说得通的候选短名单。

• 对黑客松演示和初步验证而言，结构确认属于"精修"，而非"阻塞项"。

代价： 前 20 名候选中，有些可能位于蛋白质内部（未暴露于表面），因而较难被 T 细胞接触。第二阶段会加入 AlphaFold 的 pLDDT 置信度分数作为过滤条件。

决策 4 —— 用 Python 脚本，而非 Nextflow / Snakemake

我们的选择： 使用普通 Python 模块配合 subprocess 调用，由单个 run_pipeline.py 命令行入口统一编排。

为什么不用工作流管理器：
• Nextflow 和 Snakemake 会带来学习曲线、YAML 配置和基础设施要求（Java 运行时、容器编排）。

• 对于单样本流水线（一次处理一个病例），工作流管理器的并行优势无从发挥。

• Python 脚本可读、可调试，并且无需额外运行时依赖就能部署到任何地方。

代价： 如果将来需要并行处理 50 个样本，就需要引入任务队列或工作流管理器。已记录为第二阶段事项。

决策 5 —— 用 VAF 作为克隆性代理指标，而非 PyClone-VI

我们的选择： 直接使用肿瘤 VAF（变异等位基因频率）作为"该突变克隆性高低"的代理指标。

为什么不用 PyClone-VI：
• PyClone-VI 才是正统的克隆性推断工具——它会考虑拷贝数变异，并估计携带每个突变的肿瘤细胞比例。

• 但它需要拷贝数数据，而这并非总能从单独的 VCF 中获得。

• VAF 是一个合理的代理：一个出现在 60% read 中的突变，比只出现在 5% read 中的突变更具克隆性。

代价： 在存在显著拷贝数变异的肿瘤中（晚期癌症常见），VAF 可能产生误导。第二阶段会在拷贝数数据可得时集成 PyClone-VI。

决策 6 —— 打分过程透明，不交给 Gemma 4 排序

我们的选择： 由一个确定性的 Python 函数（scoring.py）负责硬过滤与综合排序。Gemma 4 绝不参与决定哪些候选能存活。

原因：
• 临床决策需要可审计。兽医肿瘤学家或监管机构必须能够看清：为什么候选 A 的排名高于候选 B。

• 用大模型来排序候选，会引入不确定性与不透明性。

• Gemma 4 的角色是解读与沟通——它解释这份排序清单，而不生产这份清单。

打分公式：

composite_score = 0.50 × IC50_score（对数缩放，1nM 时为 1.0 → 500nM 时为 0.0）
               + 0.30 × immunogenicity_score（T 细胞激活概率）
               + 0.20 × VAF_score（归一化后的克隆性代理指标）


所有权重都明写在 pipeline/modules/scoring.py 中。要改动它们需要修改代码，而不是修改提示词。

决策 7 —— 先做犬类，后做人类

我们的选择： 面向兽医肿瘤学（犬类）构建，而非人类肿瘤学。

原因：
• 人类临床应用所需的监管路径长达数年，超出一场黑客松的范围。

• 犬类癌症在生物学上与人类癌症高度相似——相同的突变、相同的通路、相同的肿瘤抑制基因。

• 兽医肿瘤学资源匮乏。这里的可及性缺口更大，而做出演示的门槛更低。

• 在犬类中得到验证的疗法，往往会转化进入人类肿瘤学试验。

代价： 相比犬类 DLA 等位基因，预测器所用的人类 HLA 等位基因数据库和训练数据要丰富得多。NetMHCpan 对犬类的预测，其验证充分度不及对人类 HLA 的预测。

决策 8 —— mRNA 合成规格用模板生成，而非大模型生成

我们的选择： mRNA 合成规格说明（即兽医发送给 Trilink 或 Genscript 等 CMO 的那份文档）由 Jinja 模板渲染生成。患者/病例专属字段由流水线的结构化输出填充；而生产参数（加帽类似物、修饰方式、LNP 配比、QC 放行标准）则是确定性常量。

我们最初的做法： 由 Gemma 4 根据结构化提示词生成合成规格说明。后来我们把它替换掉了。

原因：
• 这份规格说明是要原封不动发给合同生产商的。一位制剂科学家只要看到一个幻觉出来的目录号、一个漂移了的 QC 阈值，或是一句推诿的话术（"请咨询您的生物信息学家"），就会否定整个工具——而且他这样做完全正确。

• 这份文档里唯一的变量就是患者/病例数据。生产科学本身是固定的：CleanCap® AG cap1（TriLink 货号 N-7413）、100% N1-甲基假尿苷替换、SM-102 LNP 按 50:10:38.5:1.5 摩尔比、RIN ≥ 8.0 放行标准，等等。

• 对于"结构确定、数据参数化"的场景，模板才是正确的工具。

实现： pipeline/templates/synthesis_spec.md.j2 + pipeline/modules/synthesis_spec.py。流水线在 mrna_design() 之后调用 generate_synthesis_spec(design_data, candidates_json_path)。

代价： 没有值得一提的代价。此前那个大模型生成的版本，并没有提供模板所不具备的价值，却带来了可衡量的风险。

这条决策所代表的原则： AI 负责解读，确定性代码负责合规。

决策 9 —— Gemma 做顾问，而非只做报告撰写者

我们的选择： 在确定性流水线之外，新增两个 Gemma 触点：

1. 运行前 VCF 顾问 —— 在提交页面、流水线启动之前运行。浏览器从上传的 VCF 中解析出结构性事实（变异数量、INFO 键、样本列、是否存在体细胞标记、染色体、FILTER 取值），发送给 Gemma。Gemma 识别出 0–3 个会实质性降低新抗原预测质量的问题（生殖系+体细胞混合、无配对正常样本、所有变异均非 PASS 等），返回带类型标记的提示（info / warning / critical）。永不阻塞提交。

2. 敏感性解读员 —— 在报告页面、流水线完成之后运行。用户拖动 IC50 与肿瘤 VAF 阈值滑块，保留/剔除的候选会在客户端即时重新排序（每次拖动不产生 Gemma 调用成本）。在用户明确请求时（"让 Gemma 解读一下"），Gemma 会写一段通俗英文，说明这种取舍意味着什么。

原因： 那种"流水线末端挂一个报告撰写器"的做法，是 Health & Sciences 赛道每一支参赛队伍都会用 Gemma 去做的事——这只是入场门槛。顾问式的定位，则把 Gemma 放到了确定性流水线确实无法胜任的角色上：在运行前推理（提前发现那些否则会让用户白算一个小时的 VCF 问题），以及在假设情景之间推理（交互式解读，而非静态输出）。

为什么这种分工对临床医生和监管机构同样站得住脚： 流水线的科学部分依然是确定性的、可审计的。Gemma 纯粹是叠加在其上的解读层——它不改变哪些候选能存活、不改变适用哪些阈值、也不改变最终交付哪条 FASTA。正是这种分离，让这个工具有朝一日进入临床场景时能够被接受。

实现：
• src/lib/vcf-stats.ts（浏览器端解析器）

• src/app/api/vcf-advisor/route.ts（Gemma 端点）

• src/components/VcfAdvisor.tsx（/submit 页面上的 UI）

• src/lib/sensitivity.ts（客户端重新排序）

• src/app/api/cases/[id]/sensitivity-narrate/route.ts（Gemma 端点）

• src/components/SensitivityPanel.tsx（/cases/[id] 与 /demo 页面上的 UI）

代价： 每次 Gemma 调用都带来延迟（约 2–5 秒）和 Vertex AI MaaS 端点上的配额消耗。运行前顾问在选择文件后自动触发（每个文件一次调用）；敏感性解读则需要用户明确点击。两者的设计都在控制成本，同时又不会让功能显得过于"斤斤计较"。
