# 关键架构决策

*Project Rosie 中每一个非显而易见的选择，以及为什么。写给未来的贡献者——或黑客松评委——让他们无需追问就能理解其中的推理。*

---

## 决策 1 — 从 VCF 开始，而非 FASTQ

**我们的选择：** 流水线以一个 VEP 注释后的 VCF 文件作为起点，而非原始测序 reads。

**我们跳过的：** 完整流水线的第 1–3 步（测序、比对、通过 BWA-MEM2 / GATK Mutect2 做变异检测）。

**原因：**
- 任何临床测序工作流都已经产出 VCF。做全外显子组测序的兽医肿瘤实验室会交付一个 VCF。
- 比对和变异检测是有成熟工具的已解决问题。加入它们会让范围翻倍而毫无新意。
- 未解决的可及性问题是从 VCF → 排序候选 → 临床报告。这正是我们要构建的。
- 对于一个 10 天的黑客松，从 VCF 开始让我们能交付一个真实、可演示的东西。

**权衡：** 用户必须提供一个已检测好的 VCF。对于 Phase 2（临床部署），我们会把 FASTQ → VCF 集成为一个可选的上游步骤。

## 决策 2 — 选 NetMHCpan 而非 MHCflurry

**我们的选择：** 以 NetMHCpan 4.2 作为结合亲和力预测器。

**为什么不用 MHCflurry：**
- MHCflurry 是 Python 原生、易于安装，但它主要是在人类 HLA 等位基因上训练的。
- 对于犬类数据（核心用例），我们需要 **DLA 等位基因支持**——HLA 的犬类对应物。NetMHCpan 支持 DLA 等位基因。
- MHCflurry 还与所装 TensorFlow 版本存在 Keras 3 不兼容，导致运行时错误。

**权衡：** NetMHCpan 调用默认通过 IEDB REST API 路由，较慢（955 个突变约 45 分钟）。本地二进制更快（约 2 分钟），但需要把 IEDB Analysis Resource 工具包作为包装器安装——独立于 DTU 二进制。目前可接受；已记录供 Phase 2 优化。

---

## 决策 3 — Phase 1 不用 AlphaFold

**我们的选择：** 在初始流水线中跳过结构验证（AlphaFold2 表面暴露检查）。

**原因：**
- AlphaFold 会显著增加计算时间和基础设施复杂度（合理速度需要 GPU）。
- IC50 结合分数 + VAF 综合已足以产出一份排序好的、临床可信的短名单。
- 对于黑客松演示和初始验证，结构确认是一种精化，而非阻塞项。

**权衡：** 前 20 名中的一些候选可能位于蛋白内部（非表面暴露），因此对 T 细胞的可及性较低。Phase 2 会加入 AlphaFold pLDDT 置信度分数作为过滤器。

---

## 决策 4 — Python 脚本，而非 Nextflow / Snakemake

**我们的选择：** 带 subprocess 调用的纯 Python 模块，由单个 `run_pipeline.py` CLI 编排。

**为什么不用工作流管理器：**
- Nextflow 和 Snakemake 带来学习曲线、YAML 配置和基础设施要求（Java 运行时、容器编排）。
- 对于单样本流水线（一次一个病例），工作流管理器的并行化收益并不适用。
- Python 脚本可读、可调试、可在任何地方部署而无额外运行时依赖。

**权衡：** 如果将来需要并行处理 50 个样本，我们将需要加入一个作业队列或工作流管理器。已记录供 Phase 2。

---

## 决策 5 — 用 VAF 作克隆性代理，而非 PyClone-VI

**我们的选择：** 直接使用肿瘤 VAF（变异等位基因频率）作为突变克隆性的代理。

**为什么不用 PyClone-VI：**
- PyClone-VI 是正确的克隆性推断工具——它考虑拷贝数变异，并估计携带每个突变的肿瘤细胞比例。
- 它需要 VCF 本身并不总是提供的拷贝数数据。
- VAF 是一个合理的代理：存在于 60% reads 中的突变比存在于 5% reads 中的更克隆。

**权衡：** 在拷贝数变异显著的肿瘤中（晚期癌症中常见），VAF 可能具有误导性。Phase 2 会在拷贝数数据可用时集成 PyClone-VI。

---

## 决策 6 — 透明评分，而非用 Gemma 4 排序

**我们的选择：** 一个确定性的 Python 函数（`scoring.py`）做硬过滤和综合排序。Gemma 4 从不参与哪些候选幸存。

**原因：**
- 临床决策需要可审计。兽医肿瘤医生或监管机构必须能确切看到为什么候选 A 排在候选 B 之上。
- 用 LLM 排序候选会引入非确定性和不透明性。
- Gemma 4 的角色是解读和沟通——它解释排序列表，而不产生它。

**评分公式：**
```
composite_score = 0.50 × IC50_score (对数缩放, 1nM 时 1.0 → 500nM 时 0.0)
               + 0.30 × immunogenicity_score (T 细胞激活概率)
               + 0.20 × VAF_score (归一化的克隆性代理)
```

所有权重都可见于 `pipeline/modules/scoring.py`。修改它们需要改代码，而非改提示。

## 决策 7 — 先狗后人

**我们的选择：** 为兽医肿瘤学（犬类）构建，而非人类肿瘤学。

**原因：**
- 人类临床使用的监管路径长达数年，超出黑客松范围。
- 犬类癌症在生物学上与人类癌症相似——相同的突变、相同的路径、相同的抑癌基因。
- 兽医肿瘤学资源匮乏。可及性差距更大，演示门槛更低。
- 在狗身上验证的治疗经常转化到人类肿瘤学试验。

**权衡：** HLA 等位基因数据库和预测器的训练数据对人类等位基因远比犬类 DLA 等位基因丰富。NetMHCpan 的犬类预测不如其人类预测验证充分。

---

## 决策 8 — 模板化 mRNA 合成规格书，而非 LLM 生成

**我们的选择：** mRNA 合成规格书（兽医邮件发给 Trilink 或 Genscript 等 CMO 的文档）从一个 Jinja 模板渲染。患者/病例特定字段从结构化流水线输出填充；制造参数（帽类似物、修饰、LNP 配比、QC 放行标准）是确定性常量。

**我们最初构建的：** Gemma 4 从一个结构化提示生成合成规格书。我们把它替换了。

**原因：**
- 规格书是要**逐字**发给合同制造商的。一位看到幻觉出来的目录号、漂移的 QC 阈值、或含糊措辞（"请咨询你的生物信息学家"）的制剂科学家会否掉整个工具——而且情有可原。
- 这份文档里所有的可变性都是患者/病例数据。制造科学是固定的：CleanCap® AG cap1（TriLink Cat# N-7413）、100% N1-甲基假尿苷替换、SM-102 LNP 以 50:10:38.5:1.5 摩尔比、RIN ≥ 8.0 放行标准等。
- 模板化是"确定性结构、参数化数据"的正确工具。

**实现：** `pipeline/templates/synthesis_spec.md.j2` + `pipeline/modules/synthesis_spec.py`。流水线在 `mrna_design()` 之后调用 `generate_synthesis_spec(design_data, candidates_json_path)`。

**权衡：** 没有值得一提的。之前的 LLM 生成版本没有提供模板不具备的价值，反而增加了可度量的风险。

**这代表的原则：** *AI 负责解读，确定性代码负责合规。*

---

## 决策 9 — Gemma 作为顾问，而非只是报告撰写者

**我们的选择：** 在确定性流水线周围新增两个 Gemma 触点：

1. **预检 VCF 顾问** — 在流水线启动*之前*运行于提交页。浏览器从上传的 VCF 解析结构事实（变异数、INFO 键、样本列、体细胞标志是否存在、染色体、FILTER 值）并发送给 Gemma。Gemma 识别出 0–3 个会显著降低新抗原预测质量的问题（胚系+体细胞混合、无配对正常、所有变异非 PASS 等）。返回类型化的建议注释（info / warning / critical）。从不阻塞提交。

2. **敏感性解说者** — 在流水线完成*之后*运行于报告页。用户移动 IC50 和肿瘤 VAF 阈值滑块；保留/剔除的候选在客户端即时重新排序（每次滑块刻度变动都不需要 Gemma 成本）。在明确要求（"让 Gemma 解读"）时，Gemma 写一段白话解读权衡。

**原因：** 一个纯粹的"流水线末尾的报告撰写者"是每个 Health & Sciences 赛道条目都会用 Gemma 做的事——入门门槛。顾问框架把 Gemma 推入一条确定性流水线真正无法执行的角色：在运行*之前*推理（捕捉否则会浪费用户一小时算力的 VCF 问题）以及在 what-if 场景*之间*推理（交互式解读而非静态输出）。

**为什么这种分工也能向临床医生/监管者自圆其说：** 流水线科学保持确定性和可审计。Gemma 纯粹是叠加在上面的解读层——它不改变哪些候选幸存、哪些阈值适用、或哪个 FASTA 被交付。这种分离正是当工具最终进入临床环境时让它可被接受的框架。

**实现：**
- `src/lib/vcf-stats.ts`（浏览器端解析器）
- `src/app/api/vcf-advisor/route.ts`（Gemma 端点）
- `src/components/VcfAdvisor.tsx`（`/submit` 上的 UI）
- `src/lib/sensitivity.ts`（客户端重排序）
- `src/app/api/cases/[id]/sensitivity-narrate/route.ts`（Gemma 端点）
- `src/components/SensitivityPanel.tsx`（`/cases/[id]` 和 `/demo` 上的 UI）

**权衡：** 每次 Gemma 调用都有延迟（约 2–5 秒）和 Vertex AI MaaS 端点的配额成本。预检在文件选择时自动触发（每个文件一次调用）；敏感性解说需要显式点击。两者都设计为在让功能感觉不到交易性的同时约束成本。
